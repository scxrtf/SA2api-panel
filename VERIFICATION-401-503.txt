VERIFICATION - 请求 503 · client（上游 401 token 失效被误当请求级错误）
日期: 2026-10-23 (Asia/Shanghai)
样本请求: id=cmvkmp1fd0054mn1th1jmslgx  model=cn:kimi-k3-1  status=503 errKind=client
          attempts=8  duration=39291ms  ttfb=0  key=SA  ua=Codex Desktop/0.162.0-alpha.2

根因（已复现，非推测）:
  1. 池内 28 个 cn 账号中 24 个的 access token 已被上游吊销：
     /v2/chat/completions 返回 openresty/APISIX 的 HTML「401 Authorization Required」（无业务信封）。
  2. classify() 对 401 无信封体落到兜底 "client"（请求级错误）：
       · chat 层不触发 refresh（needsRefresh 只看本地 expiresAt，而库里 expiresAt 是未来值）
       · applyErrorKind 对 client 不冷却、不罚号、不禁用 → 坏号永久留在选号池
  3. 每次客户端请求在坏号之间轮转：8 次 × 指数退避 500/1000/2000/4000/8000×4 ≈ 39.5s，
     与实测 33.9–46.8s 完全吻合；末端 default 分支把未覆盖类别一律映射成
     503 no_healthy_account，真因（401 token）被完全掩盖。
  4. 12 小时窗口统计：503|client 共 61 次，attempts 全为 8，跨 kimi-k3-1 / glm-5.3 /
     deepseek-v4.1-flash 与 SA / LHT / GZD 三个 key —— 是池侧系统性问题，不是单个客户端。
  5. 24 个坏号的 refresh 也无效：POST /v2/token/refresh 返回
     {"code":12153,"msg":"12153:refresh token is invalid"} → 只能重新登录恢复。

修复（3 处逻辑 + 1 处标签）:
  A. 新增错误类别 auth_expired：401 且无业务信封（hasBusinessEnvelope 为假）→ auth_expired。
     （有信封的 401 + 12153 仍走 session_dead，语义区分清楚）
  B. chat 主循环：命中 auth_expired → 复用 accountSession.withFreshAuth 强制刷新并同号重试一次
     （单飞刷新 + 死号 5min 负缓存）；刷新失败（12153/无 refreshToken）→ pool.disable 立即
     摘除该号并直接换号，不再走退避 —— 死号处理从「40s 轮转」变为「一次往返」。
  C. 请求级 4xx（400/413/422，kind=client）→ 首跳即透传上游状态码，不轮转、不退避、不罚号。
  D. 末端映射补齐：client 保留上游 4xx；auth_expired/account_fault 用独立 code；
     hard_credit 402；server 502 —— 不再一律 503 no_healthy_account。
  E. 面板标签：modelscan codeOf/stopAccount/applyOutcome 识别 auth_expired。
